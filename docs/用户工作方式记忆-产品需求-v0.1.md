# 用户工作方式记忆产品需求 v0.1

## 1. 需求概述

### 1.1 一句话定义

让 Agent 从用户在真实任务中的明确表达、最终选择、主动修改和验收结果中，逐步形成可查看、可解释、可修改、可停用的工作方式记忆，并在后续同类任务中改变计划、表达、工具选择或确认节点。

### 1.2 用户问题

用户与 Agent 长期协作时，经常重复说明相同的工作方法，例如：

- 接到模糊想法后需要先补齐目标、场景和边界。
- 哪些低风险步骤可以直接推进，哪些关键决定必须由用户确认。
- 处理知识库时应先检查结构，再选择位置并做最小更新。
- 产物生成后仍需验证真实可用性。

现有会话上下文只能维持短期连续性，无法稳定地把这些跨任务规律转化为后续行动。普通用户画像又容易停留在标签和表达偏好，无法直接改善任务结果。

### 1.3 产品目标

首版验证三个结果：

1. 用户为纠正工作方法而补充的说明次数下降。
2. Agent 首次提出的执行路径更接近用户最终采用的路径。
3. Agent 能在正确节点确认，在常规节点自动推进。

### 1.4 非目标

首版不覆盖：

- 人格、情绪、健康、政治倾向等敏感属性推断。
- 完整业务知识库和项目事实管理。
- 当前任务状态与待办管理。
- 仅用于模仿口吻的表达风格学习。
- 未经用户控制的全自动长期规则生成。

## 2. 核心产品原则

1. **行为有效**：记忆必须能影响计划、表达、工具选择或确认节点。
2. **证据优先**：用户明确声明和最终选择的权重高于系统推断。
3. **范围明确**：每条记忆必须说明适用任务、对象、项目或阶段。
4. **可解释**：Agent 应能说明某次关键行为使用了哪条记忆以及来源。
5. **用户可控**：用户可以查看、确认、修改、暂停和删除记忆。
6. **渐进学习**：一次行为只能形成候选，不直接成为长期规则。
7. **高影响确认**：方向、评价、发布、权限和不可逆动作相关规则必须由用户确认。

## 3. 记忆对象

### 3.1 首版支持的记忆类型

| 类型 | 要解决的问题 | 示例 |
|-|-|-|
| 任务启动方式 | 用户希望 Agent 怎样理解和展开任务 | 模糊灵感先发展成完整需求，再决定写入位置 |
| 决策与确认 | 哪些步骤自动推进，哪些需要确认 | 常规整理自动推进，方向与删除操作交给用户决定 |
| 信息处理 | 资料、文档和知识库按什么顺序处理 | 先查现有结构，再最小修改，最后回查 |
| 完成与验收 | 用户怎样判断任务完成 | 文件生成成功后还要验证内容和实际可用性 |

### 3.2 数据结构

每条记忆至少包含：

| 字段 | 类型 | 说明 |
|-|-|-|
| memory_id | string | 稳定唯一标识 |
| rule | string | Agent 下一次应执行的动作规则 |
| memory_type | enum | 任务启动、决策确认、信息处理、完成验收 |
| source_type | enum | 明确声明、最终选择、主动修改、验收反馈、系统推断 |
| evidence_refs | array | 对应会话、任务、修改或验收事件引用 |
| scope | object | 适用任务、对象、项目和阶段 |
| confidence | enum | 候选、较稳定、已确认 |
| exceptions | array | 不应应用的条件 |
| status | enum | 观察中、启用、暂停、失效 |
| created_at | datetime | 创建时间 |
| updated_at | datetime | 最近一次得到支持或纠正的时间 |

用户记忆、项目记忆和当前任务状态应分别存储，检索时可以组合，写回时不可混写。

## 4. 用户闭环

### 4.1 记忆形成

1. 用户完成一次真实任务。
2. 系统收集用户明确声明、方案选择、主动修改和验收结果。
3. 系统识别可能重复出现的工作规律，生成候选记忆。
4. 候选记忆保存规则、证据、范围、例外和置信度。
5. 首版由用户确认后，候选记忆才可进入启用状态。

### 4.2 记忆应用

1. 新任务进入后，系统识别任务类型、对象、项目和风险等级。
2. 仅检索范围匹配且状态为启用的少量记忆。
3. 将记忆转化为本次任务的具体行动约束。
4. Agent 在关键行为中记录实际使用的记忆。
5. 用户验收后，系统记录采用、修改或拒绝结果。

### 4.3 记忆修正

- 用户采用结果：增加支持证据，但不自动扩大适用范围。
- 用户修改结果：保留修改前后差异，并生成范围修正建议。
- 用户拒绝结果：降低置信度，必要时暂停该规则。
- 连续跨场景误用：自动暂停，并提示用户检查。
- 长期未使用：保持原状态，不因时间自动强化。

## 5. MVP 功能需求

### FR-01 行为证据采集

系统应记录以下事件：用户明确声明、方案选择、文本或结构修改、接受、拒绝及拒绝原因。系统自身生成的内容不得作为支持证据。

验收标准：任一候选记忆都能回溯至少一条用户行为证据；缺少用户证据时不得进入已确认状态。

### FR-02 候选记忆生成

系统应把行为证据提炼成可执行规则，同时生成建议类型、适用范围、例外和初始置信度。

验收标准：候选内容必须描述下一次 Agent 应如何行动，不能只生成“用户喜欢简洁”一类无法执行的标签。

### FR-03 用户确认

系统应向用户展示候选规则、来源证据、适用范围和潜在影响。用户可以确认、编辑、忽略或拒绝。

验收标准：未经确认的候选规则在首版不得影响正式任务；用户编辑后的版本保留原始候选与修改记录。

### FR-04 相关记忆检索

系统应根据当前任务的任务类型、对象、项目、阶段和风险等级检索记忆，并限制注入数量。

验收标准：不匹配作用域的规则不得注入；同一任务注入的每条规则都可返回匹配原因。

### FR-05 行动应用

Agent 应把检索到的规则落实到计划、表达、工具选择或确认节点，并记录使用情况。

验收标准：研发测试可以从运行日志中看到任务、命中规则、实际动作和最终结果之间的关联。

### FR-06 结果反馈

任务完成后，系统应记录用户对结果的采用、修改和拒绝，并关联到本次使用的记忆。

验收标准：一次反馈只能更新证据与置信度，不得直接改变其他作用域中的规则。

### FR-07 记忆管理

用户应能查看记忆列表和详情，并执行修改、暂停、恢复和删除。

验收标准：暂停后立即停止检索；删除后不再用于推理；操作记录可审计。

### FR-08 风险控制

系统不得生成或应用敏感属性推断。涉及方向、评价、发布、权限和不可逆动作的工作规则必须经过用户确认。

验收标准：预置风险测试集中的敏感推断全部被阻止；高影响候选不会自动启用。

## 6. 系统模块建议

| 模块 | 核心职责 |
|-|-|
| Event Collector | 采集用户声明、选择、修改和验收事件 |
| Candidate Extractor | 从多条证据中提炼候选工作规则 |
| Memory Store | 存储规则、证据、范围、状态和版本 |
| Memory Retriever | 根据当前任务和作用域召回少量相关规则 |
| Policy Gate | 检查敏感属性、高影响规则和确认要求 |
| Action Adapter | 将规则转化为计划、工具和确认行为约束 |
| Feedback Writer | 将采用、修改和拒绝结果写回证据链 |
| Memory Console | 为用户提供查看、编辑、暂停和删除入口 |

首版可以采用 JSON 或关系型表实现规则与证据存储，向量检索只用于候选召回，最终是否应用仍需通过结构化作用域与状态过滤。

## 7. 状态流转

```text
观察中候选 -> 用户确认 -> 启用
观察中候选 -> 用户忽略 -> 保持观察中
观察中候选 -> 用户拒绝 -> 失效
启用 -> 用户暂停或连续误用 -> 暂停
暂停 -> 用户恢复 -> 启用
任意状态 -> 用户删除 -> 删除并停止使用
```

系统不得仅凭使用次数把候选自动升级为启用。后续版本可以对低风险、重复出现且可逆的规则开放自动提升置信度。

## 8. 关键接口建议

### 8.1 创建候选记忆

输入：用户行为事件、任务上下文、关联证据。

输出：候选规则、类型、范围、例外、置信度及证据引用。

### 8.2 检索可用记忆

输入：用户、任务类型、对象、项目、阶段、风险等级。

输出：按相关性排序且通过状态与范围过滤的规则列表，以及每条规则的匹配原因。

### 8.3 写回应用结果

输入：任务、使用的规则、实际动作、用户采用或修改结果。

输出：新增证据、置信度变化、范围修正建议和风险标记。

## 9. 埋点与效果指标

### 9.1 核心指标

- 工作方法纠正次数：同类任务中，用户为纠正工作方式而追加的提示数。
- 首次行动贴合率：Agent 首版路径中被最终方案保留的关键步骤占比。
- 确认节点准确率：应确认而确认、可自动而未打扰的节点占比。
- 返工率：因工作方法不符导致的重做任务占比。
- 记忆误用率：作用域不匹配或错误套用规则的次数占比。
- 可解释覆盖率：关键行为中能够关联规则与证据的比例。

### 9.2 首版验证方法

选择至少三类真实任务，每类准备难度接近、内容不同的基线组和记忆组。由用户在不知道组别的情况下评价结果，并记录补充说明、修改、拒绝和最终采用情况。

首轮三类任务：

1. 将模糊产品灵感发展成可评审方案。
2. 判断一段产品内容应放入哪个知识库位置，并生成写入计划。
3. 审阅教师端功能方案，指出表达问题、关键缺口和用户决策节点。

首版不预设通过百分比。完成三类任务后，依据真实基线分布确定上线门槛。

## 10. 异常与降级

- 记忆服务不可用：Agent 继续完成当前任务，并明确标记本次未使用长期记忆。
- 证据缺失：保留为任务记录，不生成可应用规则。
- 多条规则冲突：优先级按用户明确声明、最终选择、主动修改、系统推断排序；仍冲突时请求用户确认。
- 作用域不明确：不应用该规则，保留为候选并补充范围。
- 用户要求暂时忽略记忆：本次任务不检索，长期状态不变。
- 用户要求清空：停止使用相关记忆，并按数据治理策略完成删除。

## 11. 研发拆分建议

### 里程碑一：受控闭环

- 事件模型与记忆数据结构。
- 人工创建和确认候选规则。
- 基于结构化范围的检索。
- Agent 运行时注入与使用日志。
- 记忆列表、详情、暂停和删除。
- 三类任务的离线对照评测工具。

### 里程碑二：半自动学习

- 从多轮行为证据中自动生成候选。
- 修改差异与拒绝原因归因。
- 低风险规则置信度调整。
- 冲突检测和自动暂停。

### 里程碑三：连续项目验证

- 用户记忆与项目记忆组合检索。
- 跨任务效果看板。
- 规则版本、范围迁移和批量治理。
- 在较少指令下验证连续项目协作。

## 12. 评审时需要确定的产品决策

1. 待确认：首版服务的正式产品载体，需要明确是星光主产品、内部 Agent 平台或独立能力服务。
2. 待确认：首版记忆确认入口，需要明确采用任务结束卡片、独立记忆中心或两者同时提供。
3. 待确认：用户修改行为的采集范围，需要明确只采集产品内编辑，还是包含外部文档回传差异。
4. 待确认：记忆删除的数据治理要求，需要明确逻辑删除、物理删除与审计保留期限。
5. 待确认：首版灰度用户范围，需要明确内部产品团队、教师种子用户或其他群体。

## 13. 一句话向研发提需求

我们希望增加一套“用户工作方式记忆”能力：系统从用户在真实任务中的明确表达、选择、修改和验收中形成有证据、有范围、可解释、可控制的工作规则，在后续同类任务中影响 Agent 的计划、工具选择和确认节点；首版采用人工确认记忆，通过三类任务的基线对照验证是否减少重复说明和返工。
