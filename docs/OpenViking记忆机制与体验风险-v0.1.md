# OpenViking 记忆机制与体验风险 v0.1

## 1. 给产品经理的结论

OpenViking 在产品中的作用可以理解为一条后台流水线：记录对话，阶段性抽取长期信息，在新问题到来前检索相关内容，再把结果作为额外上下文交给模型。

```text
用户与 Agent 对话
      |
      v
记录会话与工具结果
      |
      v
达到提交条件，抽取并归档记忆
      | 
      v
下一次提问前检索相关记忆
      |
      v
把记忆摘要注入模型上下文
      |
      v
模型生成行动和回答
```

这意味着“记住了”至少包含五个独立环节：采集正确、抽取正确、存储范围正确、召回正确、模型使用正确。最终回答变差时，仅看回答无法判断问题发生在哪一环。

当前最重要的需求不应是扩大记忆量，而应先建立可观测、可纠正、可隔离、可降级的记忆闭环。只要记忆仍会在用户不可见的情况下自动注入，错误记忆就可能持续影响模型，并让用户误以为模型能力不稳定。

## 2. 官方机制中已经确认的部分

以下内容来自 OpenViking 官方仓库中的 Codex memory plugin 文档和设计说明。它描述的是 OpenViking 的 Codex 接入实现，可作为理解现有产品接入的参照；产品当前使用的具体插件版本和配置仍需研发核对。

### 2.1 存储组织

OpenViking 使用 `viking://` 虚拟文件系统组织记忆、资源和技能。长期记忆中包含用户画像、偏好和实体等目录，历史会话也可归档并通过 URI 读取。

### 2.2 会话开始

插件在会话开始时加载用户 `profile.md`，并加载偏好与实体目录的摘要索引。默认画像注入预算为 10,000 tokens。这部分是相对固定的背景注入，与每次提问触发的语义召回分别控制。

### 2.3 每次提问前召回

每次 `UserPromptSubmit` 都会触发自动召回：

1. 插件向 OpenViking 的召回或搜索接口发送当前问题。
2. 服务端按类别配额、相关性和 token 预算组装候选内容。
3. 插件可以再调用模型压缩候选，剔除弱相关内容。
4. 结果通过 `additionalContext` 注入当前模型回合。
5. 若没有相关内容，插件可以不注入任何记忆。

默认召回上下文预算为 1,600 tokens，跨回合去重冷却为 5 轮，整体超时为 120 秒。记忆无需模型主动调用工具就能进入上下文，因此用户通常看不到本轮到底注入了什么。

### 2.4 每轮结束后的采集

每个模型回合结束时，插件增量追加用户消息、助手消息和工具结果。明显的插件包装内容会被过滤，过大的工具结果会被外置保存并留下摘要引用。

采集并不等于已经形成长期记忆。会话需要发生提交，OpenViking 的抽取器才会处理待归档内容。

### 2.5 触发提交与抽取

已确认的主要提交节点包括：

- 待处理内容达到默认 20,000 tokens，提交较早内容，同时默认保留最近 10 轮维持连续性。
- 上下文压缩前提交完整记录，避免压缩造成信息丢失。
- 会话正常结束时补齐遗漏回合并提交。
- 异常退出、旧版本客户端或提交失败时，在后续启动中通过状态文件和结束标记补偿提交。

因此，新表达的偏好未必在下一句话就成为长期记忆。它何时可被其他会话召回，取决于提交是否发生、抽取是否成功以及索引是否完成。

### 2.6 范围与隔离

官方文档支持全局、当前工作区和其他工作区等召回范围。宽松模式可能召回其他工作区内容，只是排序权重更低；多用户部署需要使用 actor 隔离并明确配置身份范围。

对正式产品而言，“排序更低”不能替代权限隔离。跨用户内容必须在检索前被硬性过滤，不能依靠相关性分数降低泄漏概率。

## 3. 目前不能从插件文档直接推定的部分

以下事项需要研发基于产品当前使用的 OpenViking 版本、服务端配置和二次开发给出证据：

1. 待确认：抽取器会生成哪些记忆类型，缺少当前服务端 extractor 配置与实际输出样本。
2. 待确认：同一事实或偏好发生变化时采用覆盖、追加、合并还是版本化，缺少冲突处理规则与接口行为。
3. 待确认：用户删除记忆后，正文、向量索引、会话归档和备份分别何时删除，缺少数据生命周期约定。
4. 待确认：召回分数的含义和线上阈值，缺少当前 embedding、reranker、查询扩展和阈值配置。
5. 待确认：产品是否启用了固定画像注入、每轮语义召回和召回压缩，缺少当前插件配置快照。
6. 待确认：当前用户、团队、项目、工作区之间如何映射 actor 与 peer，缺少租户隔离设计。
7. 待确认：OpenViking 不可用或超时时，产品是静默降级、提示用户还是阻断任务，缺少客户端异常策略。

这些内容不宜由产品侧猜测后写成既定机制。研发评审时应要求提供配置、日志或可复现实验结果。

## 4. 最容易伤害体验的故障模式

| 故障 | 用户感受 | 根因位置 | P0 防线 |
|-|-|-|-|
| 错误记忆 | Agent 坚持一个用户从未表达的偏好 | 抽取 | 高影响记忆先确认；保留原始证据 |
| 过时记忆 | 用户已经改口，Agent 仍按旧习惯执行 | 冲突与生命周期 | 新旧版本可见；明确当前生效版本 |
| 无关召回 | 简单问题被旧项目背景带偏 | 检索与范围 | 结构化范围过滤；限制数量与预算 |
| 权重过高 | 当前明确指令被历史偏好压过 | 注入与提示优先级 | 当前指令优先；冲突时不自动应用 |
| 跨用户或跨项目串扰 | Agent 提到不属于当前场景的信息 | 身份与权限 | 检索前硬隔离；隔离回归测试 |
| 隐形注入 | 用户不知道回答为何突然变化 | 交互与可观测性 | 展示本轮使用的记忆与影响 |
| 召回延迟 | 每次输入后长时间无响应 | 召回服务 | 短超时、异步指标、无记忆降级 |
| 记忆服务故障 | Agent 无法继续普通任务 | 系统耦合 | 服务失败不阻断主任务 |
| 删除不彻底 | 已删除内容仍影响后续回答 | 数据治理与索引 | 删除一致性检查；禁止残留召回 |
| 临时内容长期化 | 一次任务要求变成永久偏好 | 抽取与确认 | 区分任务状态、项目事实和用户偏好 |

## 5. 产品需求应控制的对象

OpenViking 是底层记忆基础设施，产品需求需要在它之上增加策略层和用户控制层。首版建议明确以下对象：

### 5.1 写入控制

- 哪些事件允许形成候选记忆。
- 哪些记忆类型可以自动生效。
- 哪些内容必须由用户确认。
- 每条记忆的证据、作用域、创建时间和版本。

### 5.2 召回控制

- 用户、项目、任务类型和阶段的硬过滤。
- 最大召回条数、token 预算、最低相关性和去重周期。
- 本轮临时关闭记忆的开关。
- 当前明确指令与长期记忆冲突时的优先级。

### 5.3 使用可观测性

每次任务至少记录：

- 提交给检索器的查询。
- 候选记忆、分数及被过滤原因。
- 最终注入模型的原文或摘要。
- 记忆如何改变计划、工具选择、确认节点或回答。
- 本轮延迟、超时与降级状态。

### 5.4 纠错与删除

- 用户可修改、暂停、恢复和删除记忆。
- 用户可说明“这条不对”“只适用于这个项目”“本轮不要使用”。
- 修正后旧版本立即停止召回。
- 删除动作覆盖正文、索引和缓存，并能验证后续无法召回。

## 6. 玩具实验能否帮助写需求

能，但它适合回答产品问题，不能单独证明底层算法已经可上线。

它最有价值的地方是让 Yi 亲自感受到：

- 什么样的记忆真的减少重复说明。
- 一条记忆在哪些任务中有帮助，在哪些任务中令人反感。
- 用户是否需要看到记忆命中，以及看到多少信息才刚好。
- 确认、修改、暂停和删除应该出现在任务过程的哪个节点。
- 错误记忆、无关记忆和过时记忆哪一种最难容忍。

它不能独立回答：

- OpenViking 线上召回准确率和延迟是否达标。
- 多租户隔离是否可靠。
- 删除是否覆盖所有存储副本。
- 大规模数据下的成本和稳定性。

所以实验分成两层更有效：第一层使用透明、可控的模拟记忆，打磨产品交互和判断标准；第二层接入与线上一致的 OpenViking 配置，用同一批任务验证真实抽取、召回、冲突、延迟和降级。

## 7. GUI 是否必要

GUI 对这项实验有必要，但首版只承担“看见和控制”，无需做成完整产品。

最小界面建议保留五块：

1. 当前任务与本轮记忆开关。
2. A/B 盲评结果，不提前显示哪组使用了记忆。
3. 本轮召回轨迹，包括候选、过滤、最终注入和耗时。
4. 记忆详情，包括规则、证据、范围、版本和使用记录。
5. 修改、暂停、删除以及“仅本轮忽略”操作。

Pi 终端适合调试运行过程，Codex 适合编排实验，GUI 负责让 Yi 建立产品直觉。三者职责不同，不需要让 Pi 终端承担用户体验验证。

## 8. 推荐实验顺序

### 阶段一：理解行为

用当前透明 JSON 记忆做三类任务的盲评。每次只改变“是否注入记忆”一个变量，观察记忆对行动路径和返工的影响。

### 阶段二：故意制造失败

固定测试四种记忆：正确且相关、正确但无关、错误、高度过时。观察 Yi 能否发现问题、理解来源并快速纠正。

### 阶段三：接入真实 OpenViking

冻结模型、提示词、工具和任务输入，替换记忆后端为产品同版本 OpenViking。记录抽取结果、召回候选、实际注入、延迟和错误。

### 阶段四：形成研发门槛

根据实验数据确定门槛，至少包含：误用率、隔离失败数、纠正生效时间、删除后残留召回数、P95 召回延迟、降级任务成功率和可解释覆盖率。

## 9. 评审研发时直接询问的问题

1. 当前产品使用的 OpenViking 版本、插件类型和完整配置是什么。
2. 一句话从用户说出到成为可召回记忆，经过哪些服务和异步任务，通常需要多久。
3. 当前会抽取哪些类型，能否拿十条脱敏真实样本展示原始证据与抽取结果。
4. 用户改口时，旧记忆怎样失效；两条冲突记忆同时命中时由谁裁决。
5. 召回前是否按用户和项目做硬过滤，能否提供跨用户、跨项目隔离测试。
6. 模型最终收到的记忆内容能否完整记录并回放。
7. 当前用户能否查看、修改、暂停、删除以及仅本轮忽略记忆。
8. 删除之后哪些存储仍会保留内容，多久后索引和缓存不再命中。
9. 召回超时或 OpenViking 不可用时，主任务怎样继续，用户是否会感知。
10. 当前有哪些指标能够区分抽取错、检索错、注入错和模型使用错。

## 10. 建议给研发的第一版需求表述

在现有 OpenViking 记忆接入之上增加一套可观测和可控制的记忆策略层：每条长期记忆必须保留来源证据、作用域、状态和版本；每次召回必须执行用户与项目硬隔离，并记录候选、过滤原因、最终注入内容及耗时；用户可以查看、修改、暂停、删除和仅本轮忽略记忆；当前指令优先于历史记忆；记忆服务失败时不得阻断主任务。首轮通过透明模拟实验确定交互与指标，再用产品同版本 OpenViking 完成真实链路验收。
