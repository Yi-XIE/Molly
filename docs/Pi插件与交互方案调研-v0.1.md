# Pi 插件与交互方案调研 v0.1

## 1. 决策结论

首阶段采用“Codex 自动编排 Pi + 轻量实验控制台”的混合方案。

- Codex 负责准备任务、调用 Pi、收集运行事件、生成基线组与记忆组结果，并整理对照数据。
- Yi 通过可视化界面完成盲评、查看记忆证据、确认候选规则、暂停或删除规则。
- Pi 自带终端界面只用于调试，不作为主要产品体验。
- 首阶段不安装第三方长期记忆插件，先实现实验专用的最小透明记忆闭环。
- Web Search 可以安装，但必须作为任务能力与记忆能力分离；同一次对照实验的两组必须拥有相同工具。
- MCP、多智能体和复杂自动化暂缓，等记忆闭环验证有效后再引入。

## 2. 为什么首阶段不直接使用第三方记忆插件

候选 `@remnic/plugin-pi` 能在模型调用前召回上下文，在回合后观察消息，并与长上下文归档协同。它依赖本地 Remnic daemon、连接器令牌、SQLite、LanceDB、Orama 等组件，也可以接入其他检索服务。

它适合成熟的长期记忆运行环境，但不适合当前首轮实验，原因包括：

1. 我们需要验证记忆形成、确认、召回、应用和纠错的每个环节，通用插件会遮蔽关键机制。
2. 当前需求强调工作方式规则、来源证据、适用范围和高影响确认，通用上下文记忆未必严格满足这些产品约束。
3. 自动观察完整会话容易把临时任务信息和工作方式记忆混合。
4. 引入外部记忆框架后，实验效果难以归因到规则设计、召回策略或插件自身的压缩与检索能力。

建议在第二阶段增加 Remnic 兼容性对照：用同一评测集比较自研透明闭环与 Remnic 的效果和维护成本，不在首版将其作为基础依赖。

## 3. 插件候选与优先级

| 能力 | 候选 | 首阶段决策 | 原因与约束 |
|-|-|-|-|
| Web Search 与网页读取 | `pi-web-access` | 条件安装 | 能提供搜索、正文提取、PDF 与 GitHub 内容读取；任务需要外部资料时有价值 |
| 工作方式记忆 | `@remnic/plugin-pi` | 暂缓 | 能力较完整，但会降低实验可解释性并扩大数据采集范围 |
| MCP 接入 | `pi-mcp-adapter` | 暂缓 | 可按需连接工具且支持懒加载，但首轮不需要真实外部系统写入 |
| 计划可视化审阅 | `@plannotator/pi-extension` | 不作为主界面 | 擅长计划审批和标注，不覆盖盲评、记忆证据与规则治理 |
| 终端界面增强 | `pi-zentui` | 不安装 | 只改善 TUI 外观，对实验有效性没有直接贡献 |
| 多智能体 | `pi-subagents` 等 | 暂缓 | 增加行为来源和归因复杂度，影响基线可比性 |

## 4. Web Search 安装建议

`pi-web-access` 是目前最贴近实验需求的第三方候选，但需要受控配置。

### 可用价值

- `web_search`：检索当前资料并返回来源。
- `fetch_content`：读取网页、PDF 和 GitHub 内容。
- `source_check`：针对声明生成证据检查结果。
- 自带本地短期缓存，便于复现实验输入。

### 首阶段配置原则

- 默认关闭浏览器 Cookie 读取。
- 默认关闭远程 Curator 访问，仅绑定本机回环地址。
- 不配置付费搜索提供方，避免实验中出现不可控费用。
- 优先使用明确指定的搜索路径；需要隐私控制时使用自建 SearXNG。
- 网页正文和搜索缓存只保存在实验专用 Pi 配置目录。
- A/B 两组必须使用同一插件版本、同一搜索提供方和同一输入快照。
- 对无需外部信息的记忆实验任务关闭 Web Search，减少变量。

### 安装门槛

安装前完成：

1. 固定版本并下载包内容进行源码检查。
2. 检查安装脚本、网络请求目标、文件访问范围和遥测行为。
3. 建立项目级配置，禁止读取全局浏览器 Cookie 和全局 Pi 配置。
4. 用无敏感内容的测试查询验证请求路径与缓存位置。

## 5. MCP 的角色

`pi-mcp-adapter` 可以把飞书、浏览器和其他服务按需暴露给 Pi，并通过代理工具减少上下文占用。它还涉及服务器配置、OAuth 凭据和外部进程生命周期。

首阶段只验证工作方式记忆，真实飞书写入、消息、删除和发布都不在范围内，因此没有必要立即安装 MCP。需要验证工具选择时，可以使用模拟工具事件。

进入第二阶段后，若要验证“记忆是否改变真实工具选择”，再项目级安装 MCP，并只开放：

- 飞书只读搜索和文档读取。
- 无副作用的本地检索工具。
- 受控的模拟写入工具。

任何真实写入工具保持禁用，直到单独完成权限和确认机制评审。

## 6. GUI 方案判断

### 6.1 不建议只让 Yi 使用 Pi 终端

Pi 的终端界面适合开发和调试，但不适合以下核心任务：

- 对 A/B 两个结果做隐藏组别的并排比较。
- 查看某条记忆的规则、证据、范围、例外和版本。
- 确认、编辑、暂停、恢复或删除候选记忆。
- 查看一次任务为何召回某条规则以及它改变了什么行动。
- 汇总多轮实验指标。

### 6.2 不建议完全隐藏 Pi

如果所有过程都只由 Codex后台执行，Yi 很难判断 Pi 是真正使用了记忆，还是输出碰巧相似，也无法直接看到错误召回和确认节点。

### 6.3 推荐的混合体验

```text
Yi 提交真实任务
      |
      v
Codex 生成配对实验并调用 Pi JSON/RPC
      |
      +--> 基线运行：不注入工作方式记忆
      |
      +--> 记忆运行：注入范围匹配的已确认规则
      |
      v
本地实验控制台隐藏组别并展示结果 A / B
      |
      v
Yi 选择、评分、标注修改和确认候选记忆
      |
      v
证据日志与记忆状态更新
```

Codex 可以在本地仓库中运行命令、调用 CLI，并通过脚本重复执行任务。Pi 官方支持 print、JSON 和 RPC 模式，因此可以由 Codex编排而不依赖人工操作终端。OpenAI 官方文档也确认 Codex CLI 可以运行本地工具，并可通过脚本和非交互模式组成重复工作流。

## 7. 最小 GUI 范围

首版只做四个视图：

1. **任务入口**：输入任务、选择任务类型、声明允许使用的资料和工具。
2. **盲评对照**：并排展示结果 A 与 B，不显示组别；支持选择、更正和评分。
3. **记忆证据**：展示候选规则、原始证据、适用范围、例外和本次影响。
4. **记忆管理**：确认、编辑、暂停、恢复和删除规则。

首版不做账号体系、团队协作、复杂报表、移动端适配和公开部署。界面只运行在本机，数据只落在实验目录。

## 8. 实验编排要求

- 使用 Pi JSON 或 RPC 模式，不依赖终端屏幕抓取。
- 每次运行记录 Pi 版本、模型、提示、工具清单、规则快照、输出、耗时和错误。
- 基线组与记忆组使用相同模型、思考等级、工具和输入资料。
- 两组采用独立 Session，避免上下文串扰。
- 运行顺序随机化，展示时使用 A/B 随机标签。
- 记忆组只注入作用域匹配且状态为启用的规则。
- 任何自动生成的候选规则必须等待 Yi 确认。

## 9. 实施顺序

### 第一步：无插件核心实验

- 完成 Pi JSON/RPC 调用器。
- 完成两组独立运行与运行记录。
- 完成规则注入、命中说明和证据回写。
- 用已有三类任务跑通首个端到端样例。

### 第二步：轻量 GUI

- 完成任务入口和 A/B 盲评。
- 完成记忆详情和候选确认。
- 完成暂停、恢复和删除。

### 第三步：受控 Web Search

- 审查并固定 `pi-web-access` 版本。
- 只在需要外部资料的任务中启用。
- 冻结搜索结果快照，保证两组输入一致。

### 第四步：真实工具验证

- 评审后引入 `pi-mcp-adapter`。
- 首先开放飞书只读能力。
- 验证记忆是否改善工具选择和确认节点。

## 10. 当前建议

现在先不安装任何第三方插件。下一项工程工作应是构建 Pi JSON/RPC 实验调用器和本地盲评控制台。Web Search 在调用器跑通后单独审查并安装；长期记忆插件保留为第二阶段对照方案。
