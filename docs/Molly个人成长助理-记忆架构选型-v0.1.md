# Molly 个人成长助理：记忆架构选型 v0.1

## 1. 产品名

这个玩具命名为 **Molly（莫莉）**。

Molly 是当前正式名称。她会陪伴用户积累共同经历、看见变化，并把成长落实到具体行动中。`Molly` 只有两个音节，中英文都容易称呼，后续用作语音唤醒词也比较自然。

Molly 与 Cortana 的关系可以理解为：Cortana 负责陪 Yi 设计和建造她；Molly 是逐渐长成、专属于 Yi 的个人成长助理。

## 2. 选型结论

玩具阶段建议继续采用 **Pi + OpenViking**，但不把所有记忆治理都交给 OpenViking。

推荐架构为：

```text
Molly GUI / 未来的 TTS
          |
          v
Pi：对话、推理、文档和工具执行
          |
          v
Molly Memory Policy：写入、作用域、优先级、确认和遗忘
       /        |          \
      v         v           v
关系账本     OpenViking    原始产物
SQLite/JSON  经历与资料库   文档/Obsidian/飞书
```

其中：

- OpenViking 保存大量会话经历、资料、工具结果和可检索的经验。
- Molly Memory Policy 决定什么可以影响人格和长期行为。
- 关系账本保存少量、高价值、需要准确和可编辑的当前状态。
- 原始文档与知识库保持事实来源，记忆只保存引用和必要摘要。

这套方案比单独依赖一个自动记忆插件更适合人格化助理，因为“能搜到过去”与“知道当前应该相信什么”是两种不同能力。

## 3. OpenViking 是否适合 Molly

### 3.1 适合的部分

根据 OpenViking 官方资料，它具备以下优势：

- 已有官方 Pi 扩展，可在每次提问前自动召回，并在每轮结束后采集对话。
- 会话提交后异步生成摘要并抽取长期记忆。
- 支持 `profile`、`preferences`、`entities`、`events`、`identity`、`soul`、`cases`、`trajectories` 和 `experiences` 等类型，也支持自定义类型。
- 使用 L0 摘要、L1 概览、L2 原文三级内容，适合控制上下文成本。
- 记忆、资料与技能统一使用 `viking://` 路径，便于 Agent 浏览和引用。
- 保留检索轨迹以及每次提交的 `memory_diff.json`，可以审计新增、更新、删除和跳过的记忆。
- Pi 扩展提供 `viking_remember`、`viking_forget`、`viking_search`、`viking_read` 等显式工具。
- 接管 Pi 上下文失败时采用 fail-open 策略，可退回完整本地历史或 Pi 默认压缩。

这些能力与 Molly 的经历回顾、文档协作和长期上下文非常匹配。

### 3.2 需要谨慎的部分

- 每次提问前可以自动注入隐藏记忆，错误召回会悄悄改变回答。
- 自动抽取、合并和删除由模型参与，结果具有概率性。
- 默认作用域若配置过宽，可能把其他工作区内容带入当前对话。
- 画像和召回会占用上下文预算，并增加响应延迟。
- 主项目采用 AGPLv3，未来做闭源商业产品前需要法务和研发确认部署及修改方式。
- 官方基准能说明技术潜力，但不能替代 Molly 自己的长期关系、纠错和用户信任测试。

因此，OpenViking适合做 Molly 的上下文数据库和经历仓库，不宜直接成为人格真相的唯一来源。

## 4. 候选方案比较

| 方案 | 擅长领域 | 对 Molly 的价值 | 当前判断 |
|-|-|-|-|
| OpenViking | 会话归档、分层上下文、资料与记忆统一、检索轨迹 | 与 Pi 有官方扩展，适合个人资料和共同经历 | 作为主记忆后端 |
| Mem0 | 从消息抽取事实并执行新增、更新、删除，按用户、Agent、会话划分范围 | 接入简单，适合偏好和事实型记忆 | 可做第二阶段对照，不急于引入 |
| Letta | Agent 状态、核心记忆块、完整消息和工具持久化 | 人格与核心状态常驻上下文的思路值得借鉴 | 架构较重，且会与 Pi 的 Agent 内核重叠 |
| Graphiti | 带时间和来源的事件、实体与关系图 | 适合成长轨迹、人物关系和“当时有效、后来改变” | 关系复杂后再考虑，不用于首版 |
| LangMem | 语义、情景、程序性记忆的抽取与更新方法 | 适合设计 Molly 自己的记忆策略和结构 | 借鉴模型，暂不增加运行依赖 |

没有一个现成方案能直接提供完整的“人格化成长伙伴”。真正形成产品差异的部分，是 Molly 如何选择经历、确认变化、处理冲突和发起复盘。

## 5. Molly 的六层记忆

### 5.1 核心人格

内容包括 Molly 的身份、价值边界、表达方式和主动性规则。由开发者与 Yi 共同设定，禁止通过日常对话自动改写。

示例：温柔但有判断；涉及不可逆操作前确认；算命内容明确属于娱乐体验。

### 5.2 用户当前画像

保存少量当前有效的结构化信息，如称呼、职业角色、长期方向、协作偏好。用户可直接查看和编辑；新信息与旧信息冲突时，先形成修改建议。

### 5.3 目标与承诺

保存当前目标、决定、计划、复盘日期和未完事项。它有状态机和截止时间，不能仅靠语义检索。

### 5.4 共同经历

保存一次值得回忆的完整事件：当时情境、Yi 的判断、Molly 的行动、结果、用户反馈和后续影响。OpenViking 的 events、cases、trajectories 与 experiences 可以承载这一层。

### 5.5 工作方法

保存经过证据支持的协作规则，例如怎样改文档、何时查知识库、哪些决定需要确认。这类记忆必须有作用域、例外和版本。

### 5.6 原始历史与资料

包括完整聊天、文档、网页、工具结果和知识库内容。主要用于检索和追溯，不应直接当作当前事实全部注入。

## 6. 写入策略

### 6.1 立即写入

仅处理用户明确表达的命令：记住、忘掉、改成、只用于这个项目。写入后立即向用户展示结构化结果。

### 6.2 回合后候选

对偏好、工作方法和成长变化先生成候选，保留原始证据。低影响候选可以等待每日整理，高影响候选必须由用户确认后生效。

### 6.3 每日经历卡

从当天对话与完成的工作中生成少量经历卡：做了什么、有什么决定、情绪或判断发生了什么变化、接下来可能继续什么。用户可以保留、编辑或丢弃。

### 6.4 周期复盘

每周从经历卡、目标变化和文档成果中生成复盘草稿。复盘本身先作为产物，不自动把模型的推断写回用户画像。

## 7. 召回策略

一次对话按确定顺序组装上下文：

1. Molly 核心人格。
2. 用户当前画像中的少量稳定字段。
3. 当前目标和任务状态。
4. 与当前问题相关的工作方法。
5. 最多三条相关共同经历。
6. 按需读取的原始文档与历史。

当前用户指令高于历史记忆。记忆间冲突时使用时间、作用域、用户确认状态和证据强度判断；仍无法确定时不注入冲突结论，并把冲突交给用户处理。

## 8. 首版实施方案

### 阶段一：透明玩具

- 使用现有 Pi。
- 关系账本先用 JSON，稳定后迁移 SQLite。
- OpenViking 先运行在本机，关闭跨工作区宽松召回。
- GUI 展示本轮引用的记忆、来源和影响。
- 支持记住、修改、暂停、忘记和仅本轮忽略。
- 自动生成每日经历卡，周复盘由用户主动触发。

### 阶段二：真实使用

- 接入 Obsidian 与飞书只读，写入操作单独确认。
- 增加目标与承诺状态机。
- 加入错误、过时、无关和冲突记忆测试集。
- 记录召回准确性、延迟、纠正生效和删除残留。

### 阶段三：人格与声音

- 接入流式 TTS 和语音输入。
- GUI 形象只表达说话、倾听、思考和完成等有限状态。
- 评估主动复盘和提醒的合适频率。
- 共同经历关系变复杂后，再评估 Graphiti 时间图谱。

## 9. 当前推荐配置原则

- OpenViking 的 peer 明确绑定 Molly 的个人空间和项目空间。
- 每次召回设置较小预算，先重精度再扩召回量。
- 保留并展示 `memory_diff.json` 对应的变化记录。
- 核心人格和高影响用户画像不允许后台自动覆盖。
- OpenViking 不可用时，Pi 仍能聊天和完成文档任务。
- 删除记忆后，同时检查正文、索引、缓存和关系账本。
- 暂不同时安装第二套自动记忆插件，避免重复抽取和互相污染。

## 10. 最终建议

Molly 的首版无需更换 OpenViking。更好的方案是在它上面增加一层小而明确的 Molly Memory Policy，并把少量关键关系状态单独保存。这样可以利用 OpenViking 的 Pi 集成、经历抽取、分层检索和审计能力，同时让人格、目标和用户控制留在产品自己手中。

等 Molly 连续使用两到四周后，再用同一批对话对 Mem0 做离线对照。如果时间关系和人物关系已经复杂到普通检索难以回答，再引入 Graphiti；在此之前，保持系统简单更利于定位体验问题。
